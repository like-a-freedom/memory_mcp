## Reader: что исправлено и что измеряется

Shared observer сохраняет logical/case/role/request/attempt IDs, durable start до dispatch, terminal/error/finish_reason/usage и elapsed. SDK retries выключены; новый reader protocol использует retry0 и конечные call/capture deadlines. Unknown prefill/generation/startup остаются null. Loopback adapters запрещают redirects/proxies; controlled tests покрывают timeout, disconnect,429, malformed envelope/JSON, trickling peer и cleanup. Большое число POST-строк сервера не подменяет число измеренных попыток.

Исходные independent short/long контроли отвергли гипотезу, что одной структурированной подачи достаточно. Поэтому новый вариант `ordered-relations-final-first` сохраняет весь source с ID/offsets и добавляет отношения всех структурных групп: соседние peers, пустой интервал и конец только доказанно закрытого однородного списка. Проекция не получает вопрос, accepted answer или gold ID. Неоднородные, вложенные, обрезанные и виртуализированные группы не превращаются в ложный конец. Прямые ссылки внутри `list` без `listitem` остаются без структурной аннотации, но исходный текст сохраняется.

Условный full-history reader не активирован:0/7 вызовов по заранее заданному stopping rule. Этот protocol не повторяется до успеха, labels и defaults не меняются. Нельзя автоматически расширять старые ответы или ослаблять gold, чтобы объявить этот capture успешным.

## Динамические навыки: где именно теряется результат

Реальные native MCP/CLI операции отделены от controlled ответов для pagination, partial/pending, import и reembed. Controlled import не означает реального чтения файла/сети; controlled reembed не означает реального преобразования пользовательской базы. Task-selected reference reads, фактические calls, stdout/stderr/exit, возвращённые IDs и каждый модельный ответ сохранены. ## Практическая интерпретация

Сильная сторона системы — проверяемые границы: bi-temporal/authority сценарии, source identity, неизменность фактов при heat updates, перенос и обратное восстановление статистики. Эти контракты подтверждены конечными детерминированными сценариями; их можно воспроизвести без модельного сервера. Восстановленный закрытый снимок позволяет менять retrieval без повторной дорогой formation.

Основная слабость — превращение найденного текста в достаточное и правильно использованное свидетельство. До исправления отбора нужный источник922 был в базе и среди допущенных кандидатов, но не в доставленном контексте. Отдельно reader ошибался даже при достаточном source. Формат, наличие буквальной цитаты и выполненный tool call сами по себе не подтверждают правильного решения агента. Поэтому следующий прирост следует искать на установленной границе, а не в общем увеличении top-k, token caps или числа повторов.

Измеренная precision extraction стала лучше, но полнота не выросла. Для практического использования это означает меньше ложных сущностей при сохранённых пропусках; этого недостаточно, чтобы обещать полное восстановление знания по любому вопросу. Динамические навыки обнаружили незавершение и пропуски обязательных действий, а не доказали, что более длинная инструкция улучшит поведение. Обоснованная следующая мера — короткая автономная квалификация с измеренной стоимостью и точным выходным критерием.

## Уточнение границы оптимизации retrieval

Проверка текущих исходников подтверждает: `knowledge/queries.rs::build_select_lexical_candidate_batch_query` уже сортирует узкие per-term записи и загружает payload после объединения. Предлагать этот приём как отсутствующий неправильно. `memory/retrieval/pipeline.rs::retrieve_fact_channels` отдельно выполняет direct и alias-expanded чтения, сохраняя разные native/alias роли. Исторические V5 receipts показывают два247-record пула по89 863 088 content bytes и90 словарей для922, два260-record пула по97 376 877 bytes и104 словаря дляd6. Это логические суммы повторяющихся проекций, не RSS, сетевой трафик или прочитанные engine bytes; равные totals не доказывают равные строки.

Более узкая гипотеза перед DB-cache: повторно использовать только чистые словари по **точным** content/index-key входам в пределах одного assemble. В `lexical.rs::lexical_candidate_features` структура `ContentLexicalFeatures` содержит не только vocabulary, но и **query-dependent `best_terms`**; anchor weights также зависят от текущего пула. Перенос существующего cache целиком между direct/alias запросами с ключом только content исказит ranking. Следовательно, сначала отделить измерение query-independent tokenization от query-dependent matching/anchor/ranking; при прототипе переиспользовать только первое. Не удерживать неограниченные копии больших payload ради cache hit и не выводить равенство из одного source ID или digest без проверки точных данных.

Детерминированные контроли следующего прототипа: одинаковый source с разными query terms должен сохранять разные `best_terms`/ранги; одинаковый content с другими index keys — разные index признаки; изменение списка/порядка кандидатов — прежние pool-relative weights и tie order; изменённые cutoff/access/types/revision не получают закешированные DB rows. Через существующий публичный assemble seam сравнивать полные ordered fact/source IDs, provenance, temporal selectors и content/quote bytes, а не только число результатов. Лишь затем один заранее ограниченный local alternating cost comparison с сохранёнными faults и памятью; выигрыша пока не заявлено. Это уточнение плана по фактическому коду, не реализованный cache и не новые benchmark результаты.

## Следующий extraction-диагноз: измерить границу, не расширять grammar вслепую

Текущий `extract_entities` сначала вызывает выбранный NER, затем добавляет только ограниченный grammatical subject, затем выполняет scalar admission и resolve. `grammatical_subject_candidate` срабатывает лишь на explicit subject или на единственный поддерживаемый reporting marker; предложения `3M manufactures adhesives.` и `Studio 54 reopened.` таких markers не содержат. Это объясняет отсутствие grammar fallback по исходникам, но ещё не устанавливает, выдавал ли NER кандидата и на какой границе он исчез. Старый capture сохраняет только конечные entities/facts/links, поэтому приписывать все FN admission было бы неверно.

Следующий вертикальный TDD-срез: через существующий public extraction seam сохранить наблюдаемые candidate receipts выбранного provider и конечные identity/source links для новых alphanumeric и common-noun противоположных примеров. Зафиксировать exhaustive span/role oracle и canonical-name policy до outputs. Затем исправлять только установленную границу; не добавлять `manufactures`/`reopened` или названия брендов как whitelist ради этих четырёх раскрытых предложений. Для observational capture отдельно нужны bounded startup/calls и запись каждого terminal до следующего случая: нынешний ignored16-case probe пишет общий JSON после цикла, поэтому его файл не доказывает сохранение частичного прогресса при аварии процесса. Старые16/16 completed и P.75/R.667 остаются прежними измерениями; это ограничение будущей диагностики, а не обнаруженный пропуск в их denominator.
