# SurrealDB Query Efficiency Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Устранить подтверждённую лишнюю SurrealDB работу и schema upgrade gap без потери retrieval quality, recall, performance, memory bounds и durable semantics.

**Architecture:** Query optimizations остаются в owner stores и domain retrieval/lifecycle use cases. Provisioning владеет schema readiness/upgrade policy, infrastructure — bounded sessions, clock/cadence и DB adapters. Existing narrow ports, one Active Namespace и immutable migrations сохраняются; независимые изменения проходят отдельные RED/GREEN/evidence gates в одном согласованном плане.

**Tech Stack:** Rust1.99.0, Tokio, SurrealDB/SDK3.3.2, existing eval-harness/QueryObserver, Prometheus/gcx, current GitHub pipeline; новых зависимостей/runner по умолчанию нет.

**Spec:** [Design and gates](../specs/2026-10-14-surrealdb-query-efficiency.md); [Audit/evidence](../../performance/surrealdb-query-audit-2026-10-14/audit.md).

## Global Constraints

- Baseline `bb4e9208c3054811e4fb883f28ad2145c4be65e7`; source tree имеет чужие для этой задачи CI edits — сохранить отдельно.
- Rust `1.99.0`; server/SDK `3.3.2`; exact server image digest в idle evidence.
- Production read-only до отдельного rollout authorization. Сейчас создаются только документы/evidence.
- Не менять immutable migration scripts/checksums; новый migration/dependency требует согласования AGENTS.md до реализации. Предпочитать existing053–055, не duplicate indexes.

- DDD/SOLID: owner use cases + narrow ports; transport thin; no new MemoryService dependency/business logic `service/`; DRY temporal/record/outbox/metrics helpers, без generic cross-owner query API.
- Quality-affecting constants/terms/limits/ranking/admission/threshold/K/EF/precision/model и API surface не менять.
- Unit tests pure/control ports; real DB/network/filesystem — integration. RED наблюдается до code edits, не compile failure из-за неверного setup. Barriers/controlled clock, no sleeps; каждый task отдельный commit после GREEN.
