## Storage and write path

- Add one Memory-owned `fact_access` table in the existing namespace. Use one deterministic record key per fact using the same validated key as `fact:<key>`. Keep `source_episode`, a signed 64-bit `access_count`, and an optional `last_accessed` datetime. Use only the record key for fact lookup and a `source_episode, last_accessed` index for archival lookups, subject to the prototype query plan.
- Keep the writer in `memory/fact_access_store.rs` with its existing typed, namespace-bound inputs. Use one atomic database statement or transaction per logical increment. Apply the existing saturating arithmetic and supply the same clock value for each attempt. Preserve the current return boundary and failure handling, namespace binding, typed key validation, and absent-fact no-op. Maintain the per-fact order of repeated requests.
- A fact with no previous heat has no side record. On first access, create it with source identity taken from the persisted fact, within the same transaction as the increment. On subsequent access, write only `fact_access`. Validate the existence/creation branch on the pinned engine, including two simultaneous first accesses, retry, and arbitrary bound keys. Count the indexed fact lookup on first access in the prototype. The fact record remains the source for temporal validity, visibility, and identity.
- Register the table under `MemoryTables`. `FactAccessStore` records increments, reads batched stats for exact fact keys, and finds recently accessed source episodes. Memory composes these calls with its existing Knowledge read ports. Knowledge continues to own fact queries independently. ## Upgrade and rollback

Use a new additive versioned migration in the base catalog for stdio and SaaS. Include the table and index in schema readiness, the tenant readiness digest and the owner partition. Keep all prior migration checksums and legacy columns intact. Before enabling the new writer in a namespace, backfill exact count, timestamp and source identity from legacy facts with a nonzero count **or** a timestamp. This includes negative counts and zero-count facts with timestamps. Use a bounded keyset cursor over persisted fact identity, validate identifiers and equality of pre-existing side rows, and commit each batch and its cursor together. An interrupted batch must replay without double-counting or clobbering a newer row. Reconcile eligible legacy rows and their side rows before readiness. Empty stores take the same path and require no seed. [Base catalog and tenant digest](../../../crates/memory-mcp/src/storage/migrations.rs#L163) · [Startup readiness](../../../crates/memory-mcp/src/storage/migrations.rs#L473)

Fence old writers and background workers in each namespace during backfill and switch both reads and writes as one cutover. Verify backup and restore before cutover. A binary rollback can use the retained legacy columns before side-table writes begin. After the switch, a rollback requires stopping writers and replaying exact final side-table values into the old fields with reconciliation, or restoring a verified snapshot and accepting its recovery point. Require a tested rollback path before deployment. Keep historical restored snapshots and failed receipts immutable and migrate disposable copies for evaluation.
