# Anthropic “The components of agent memory”: applicability to Memory MCP

- **Date:** 2026-11-10
- **Status:** Research addendum and conditional experiment, not authorization to build an always-on consolidation worker
- **Primary source:** [Anthropic, “The components of agent memory”](https://www.anthropic.com/research/components-of-agent-memory), published 2026-11-06; checked with `keenable-cli`
- **Related contracts:** [decision-grounded quality](2026-11-09-decision-grounded-memory-quality-design.md) and [agent outcome evaluation](2026-11-09-agent-memory-outcome-evaluation-design.md)

## What the article establishes

Anthropic describes memory written during work, later transcript-grounded “dreaming,” navigational wikis, and a small session-start index. These are experiments with Claude Managed Agents, file-backed memory, particular models and task environments. The proposed mechanisms are transferable hypotheses; the reported gains are not an expected effect size for this Rust MCP server.

The linked [sleep-time compute paper](https://arxiv.org/abs/2504.13171) reports gains on modified reasoning tasks and a SWE case study; it does not validate transcript-grounded correction or wiki retrieval in this product. Anthropic's [Dreams API documentation](https://platform.claude.com/docs/en/managed-agents/dreams) calls the feature a research preview and describes an asynchronous job that creates a separate output store while leaving its input untouched. That copy-and-review boundary is a useful design pattern. It does not imply that an always-on model job is safe, affordable, or entitled to read every tenant's transcripts.

## Current project fit

The project already preserves raw episodes and provenance, projects accepted lifecycle events in a background job ([projection](../../../crates/memory-mcp/src/service/agent_memory/projection.rs)), rebuilds graph communities, and retrieves community-linked facts. The present [community summary](../../../crates/memory-mcp/src/memory/community_summary.rs) is a short label of member entity names, not a source-quoted wiki or navigational index. The documented [procedural-memory gate](../../evals/PROCEDURAL_MEMORY.md) requires trusted outcomes and operator review before promotion; no article example justifies bypassing that policy. Current lifecycle [release evidence](../../evals/AGENT_MEMORY_LIFECYCLE.md) covers capture/projection and security risks, but not a model-agent sequential learning curve or the net value of offline consolidation.

The product is a protocol-agnostic memory service used by multiple hosts and models. A host may know its task goal, user feedback and session boundary; the server may not. An agent's untested theory is distinct from a verified outcome. A host can supply source-labeled feedback or intent through an authorized path, but the server must not infer truth from an agent's own success claim. The current source-authority and bi-temporal designs apply to any new derived view.

## Decisions and possible implementation seam

1. **Add to evaluation now:** a held-out, sequential-feedback mode with multiple independent task sequences, delayed **oracle-verified** feedback, later related tasks, misleading untested theories, changed facts and explicit stateless control. Measure learning gain over the same fixed agent without persistent memory, plus paired incumbent-versus-candidate differences at the sequence level. Include the time and tool cost of writing/reading memory. This changes the [evaluation specification](2026-11-09-agent-memory-outcome-evaluation-design.md), not production code today.
2. **Pilot source-grounded offline repair:** first build an **evaluation-only arm** in `eval-harness`, using disposable stores, controlled sources and shadow derived outputs that cannot reach a live read path. On that isolated snapshot, let a bounded pass compare candidate facts/notes/procedures against authorized source episodes and oracle-verified outcomes, flag unsupported or stale material, and propose a versioned corrected view. Preserve source spans, actor/tenant/scope, input revisions, the validation result and the reason for change. A failed pass leaves the incumbent view intact. In a later product design, publication would require committed revision semantics plus source-support and temporal/access checks; contested facts and procedural promotion still follow their separate owner-review policies. No raw source deletion, silent rewrite or hidden model decision. Decide whether to wire a production worker only after the evaluation arm shows a benefit within preregistered total-cost bounds.
3. **Pilot navigation + search separately:** build a small, scoped index of links to current evidence or independently validated derived pages, with coverage/freshness metadata and a source-search fallback. The index cannot become the sole evidence or inherit more authority than the sources. A host may load a bounded index at session start only after a separate prompt-budget and wrong-note experiment. Compare direct search, **index-guided source dereference without search fallback** (a diagnostic arm that abstains on an index miss), and index plus search fallback at the same online budget; charge index build/maintenance separately. If a single-source query already succeeds cheaply, the index should not be injected or traversed by default.
4. **Defer automatic salience gates and fixed note hierarchies:** the article's cross-model examples argue against copying its write rules into a model-independent server. A model-proposed “important” label can be stored as attributed input, never as a trusted truth or access grant. Test whether host-supplied goal/feedback labels add predictive value on held-out tasks before changing the public interface.

If either pilot becomes a product design, its use case belongs in the owning memory/knowledge context behind narrow ports; a worker is only a scheduler. Use an idempotent durable job and a committed input revision, publish derived versions atomically with compare-and-swap or equivalent conflict detection, and keep old versions queryable under `known_at` **only within current access authority**. Pin every input dependency and recheck its revision, source validity and access at publication. A revoked or newly inaccessible source must suppress dependent derived output immediately and trigger repair; a historical `known_at` query cannot restore revoked current permissions. Derived visibility is no broader than the intersection of its supporting sources' current permissions. Namespace, tenant, scope and access checks cover source reads **and** derived outputs. Bound sessions/bytes/tokens, concurrency, retries and dead letters. The output is a candidate representation, never a replacement for the raw episode. A new MCP tool, migration or dependency requires the repository's usual ADR/approval path; none is assumed here.

## Falsifiable experiment and stop rules

Use the [agent-task harness contract](2026-11-09-agent-memory-outcome-evaluation-design.md) with two complementary sets: (a) multiple independent sequential task streams that reveal feedback and rules over time, and (b) multi-source questions where an index could reduce search effort. In each set, compare the **actual incumbent MCP behavior** with offline repair alone, index alone and their combination only when applicable. A direct-search-only arm is an additional diagnostic ablation if it differs from the incumbent; it is not the promotion comparator. Keep agent/reader, source history, token budget and query order fixed; use isolated snapshots and a sealed holdout. A no-memory/stateless arm measures the value of *having* persistent memory, while incumbent-versus-candidate measures the value of the proposed change. Freeze the exact point at which offline work completes before the next task. Record wrong-note persistence, source citation accuracy, missing-source rate, final task success, call/repair burden, latency, full build + maintenance + query tokens/cost, storage and breakeven query count. Report quality by multi-source versus single-source and stable versus changing data. Do not pool a model upgrade or prompt revision into the memory-method comparison.

Reject or leave experimental any arm that fails temporal/access/source-support invariants or worsens downstream agent tasks. For a **cost-saving claim**, require the preregistered target workload to exceed the measured build/maintenance breakeven volume; for a **quality claim**, require a reproducible held-out task gain over the actual incumbent within a preregistered ceiling on total cost. Direct search remains a diagnostic comparator for explaining where an index helps. An inconclusive small sample stays inconclusive. Do not promote a procedure from an unverified transcript, inject an unreviewed note into every session, or infer a universal retention rule from the Pokémon file counts. No code or benchmark run is claimed by this document.
